# github-review-bot

Standalone GitHub Architecture (A) and Intent (B) Review Bot (`review_bot`) implementing Port-Adapter (Hexagonal) Architecture.

## Requirements
- Python >= 3.11
- uv >= 0.10.0

## Quickstart

Initialize environment and install dependencies:
```bash
uv sync
```

Run CLI:
```bash
uv run review-bot --help
```

Run tests:
```bash
uv run pytest
```

## GitHub App service (operator-prepared)

The default path is **App installation → repository selection → signed PR event → SQLite lease → A architecture review → create or update one A comment**. Explicitly available/selected B intent review uses the same Worker, with separate files, receipts and an independently approved publication gate. The CLI composes the existing signed FastAPI receiver, SQLite job store, installation-scoped GitHub/repository adapters and `WorkerLoop`; it does not install an App or deploy a service.

- **D1 — installation-based eligibility:** repositories selected during installation are eligible without operator registration. Empty `service.installation_allowlist` and `service.repository_allowlist` allow installed repositories; nonempty lists add restrictions. Installation/repository binding and installation-token scope still apply.
- **D2 — publication default:** `execution.mode: github_app` defaults to `publish.mode: comment` when the publication mode is omitted. Offline/local CLI review retains the `artifact_only` default. An operator can explicitly select `artifact_only` to keep results private without GitHub writes.
- A comments use `<!-- review-bot:architecture:v1 -->` by default and update an existing bot-owned marker comment rather than creating one per run. Ambiguous or foreign-owned markers fail closed. No automatic approval or request-changes review is submitted; draft comments are disabled by default.

### App permissions and configuration

Prepare a GitHub App with **Contents: read** and **Pull requests: write** (GitHub's implicit Metadata read permission remains). Subscribe to `pull_request`, `installation` and `installation_repositories` webhook events. PR handling covers `opened`, `synchronize`, `reopened`, `edited`, `labeled`, `unlabeled`, `ready_for_review` and `closed`; installation deletion/suspension and repository removal cancel affected work. Configure a webhook secret and an operator-managed HTTPS endpoint forwarding to `POST /webhook`; the receiver binds to loopback by default.

Supply an operator-owned, full **schema-version-2** configuration using `--config`. No configuration file or image is generated by the service commands. Architecture fields below apply to A, not B-only execution:

| Field | Required setting |
| --- | --- |
| `execution.mode`, `execution.backend` | `github_app` |
| `execution.worker_concurrency` | `1` (default) or `2`; larger values are rejected |
| `model.max_concurrency` | `1` (default) or `2`; the shared model-admission group never exceeds two |
| `service.worker` | `synchronous` |
| `service.sqlite_wal`, `service.lease_and_generation_fencing` | `true` |
| `architecture.isolation.runtime` | `rootless_docker`; no host subprocess fallback |
| `architecture.isolation.network`, `read_only_root`, `no_new_privileges` | `none`, `true`, `true` |
| `architecture.tool_image_digest` | A trusted, preloaded image's exact `sha256:<64 lowercase hex digits>` or `repository@sha256:<64 lowercase hex digits>`; null, tags and malformed pins are rejected |

`execution.available_modes` defaults to `[architecture]`; add or select `intent` explicitly for B. A-only configuration/pin checks and canonical hashes remain compatible. B-only may omit `architecture`. In mixed configurations, A preparation errors fail A without suppressing B; selected A still requires the same pinned-image/rootless checks and has no host/rootful fallback.

### Private environment and Ubuntu preparation

The configuration stores **environment variable references**, not raw secrets. References can be changed using the corresponding `service.*_env` fields; their defaults are:

| Reference field | Default environment variable | Operator-provided value |
| --- | --- | --- |
| `service.app_id_env` | `REVIEW_BOT_APP_ID` | GitHub App's positive decimal ID |
| `service.app_private_key_file_env` | `REVIEW_BOT_APP_PRIVATE_KEY_FILE` | Absolute path to an owned, regular private-key file, mode `0600` or read-only `0400` |
| `service.webhook_secret_env` | `REVIEW_BOT_WEBHOOK_SECRET` | Webhook signing secret from the operator's secret facility |
| `service.state_root_env` | `REVIEW_BOT_STATE_DIR` | Absolute, private service-state directory shared by the receiver and its one or two workers |

Do not commit the key, secrets or private state. Paths must not contain symlink components; root/HOME state paths, shared state directories, foreign ownership and linked database/key files are rejected. Existing unsafe permissions are not repaired. State/cache/analysis/artifact directories are created with mode `0700`, SQLite database and sidecars must be `0600`, and service execution uses `umask 077`, restoring the caller's mask on exit. Key reading, JWT signing and GitHub access occur only after a run is claimed; `/health` is liveness, not proof that credentials or publication work.

For **A**, prepare **Ubuntu with a rootless Linux Docker daemon**, delegated cgroup v2/systemd memory, swap, CPU and PID limits, and the trusted pinned image already available locally. The worker and daemon must belong to the same host UID; private bind-mount access still requires deployment validation. Rootful Docker and Docker Desktop are not fallback options. The image must already contain `/usr/local/bin/python3`, the trusted installed `review_bot` package and locked PMD 7.3.0/JDK 21 artifacts for the fixed `/usr/local/bin/python3 -I` container invocation. Image provenance is the operator's responsibility: there is no automatic pull, build, host JDK provisioning or target-build-script execution. **B-only requires none of these Java/analysis-image prerequisites.**

### Commands and verification boundaries

With the configuration, private state and secret references prepared, run the receiver and worker in separate processes with the same state-root value:

```bash
uv run --locked review-bot webhook --config /home/review-bot/operator.yaml --host 127.0.0.1 --port 8000
uv run --locked review-bot worker --config /home/review-bot/operator.yaml
```

For bounded processing:

```bash
uv run --locked review-bot worker --config /home/review-bot/operator.yaml --once
```

`--once` exits `0` for an empty queue or successful processing, including normal skips/cancellations; an unsuccessfully processed claimed run exits `1`. Startup/configuration failures also exit nonzero. Continuous processing reuses `WorkerLoop`'s signal-based shutdown, and both service commands close their SQLite store on exit. The analyzer is constructed/preflighted only after A is selected; an empty queue or B-only selection never initializes it.

Without a model profile, A model review is explicitly `not_run`; static analysis/delta and that limitation can still appear in the comment. Lease/generation fences, PR head/base freshness checks, event coalescing and close/revocation cancellation remain active. Cancellation does **not** delete retained source/artifacts: `artifacts.retention_days` defaults to 30, but **TTL/data-cleanup automation is not implemented**. An approved operator-owned retention/deletion procedure is required before production use; private inputs must not be published to public CI.

Automated service CLI tests use in-process signed FastAPI requests, real SQLite and `WorkerLoop`, with mock GitHub/repository/analyzer boundaries and a fake server runner. Existing integration tests separately exercise local Git/PMD/CPD and the A pipeline against mock GitHub. This is **not** live App installation, live comment publication, a deployment/public release or an Actions cutover. Actual Ubuntu rootless execution, UID bind access and live GitHub/model behavior on this service path remain unverified.

### Two workers and shared model admission

The receiver stores accepted work before returning `202`; it does not wait for analysis or model execution. Continuous workers poll the existing SQLite queue when idle (default one second), not cron. With `execution.worker_concurrency: 2`, the service runs two independent Workers with separate DB connections, leases and App adapters, and shared shutdown. The atomic claim admits at most **two live leases** across processes sharing that jobs DB and at most **one live lease per repository/PR**. Third and later requests remain queued. New events still coalesce to the latest PR generation; expired leases can recover, but execution is not exactly-once. `--once` still claims only one task.

Every actual model HTTP request uses a separate **shared SQLite admission group**, including selection, native/legacy token measurement, review, retries and warmup. For me707/Ollama, set `REVIEW_BOT_MODEL_STATE_DIR` to the same absolute, owned private directory in **every participating Worker and evaluation CLI** for the same GPU/model group. If omitted, all processes under the same OS account use `~/.local/state/github-review-bot/model-admission`. The isolated [MacBook profile](#macbook-local-llamacpp-explicit-opt-in) uses its own group/variable instead. Different group directories, other OS accounts and non-bot clients are not controlled by this limit. A caller configured for one request can conservatively lower active group concurrency; neither setting enables parallel stages inside one PR.

The admission DB stores reservation tokens/state/deadlines/limits, never prompts, source or credentials. Directories are `0700`, DB/sidecars `0600`; unsafe paths/ownership fail closed. Waiting consumes the original request/task deadline, and queued calls recheck worker cancellation and generation/lease fences before HTTP. Unused reservations can expire. **A sent generation with a lost response or crashed caller is not automatically freed by TTL:** the server may still be running it. Capacity remains conservatively reserved until actual server idleness is confirmed and an operator uses `SQLiteModelAdmission.resolve_uncertain(token, confirmed_idle=True)`. There is no automatic reconciliation or recovery CLI; never clear that state merely to bypass the limit.

The llama.cpp deployment contract additionally requires **one actual generation slot per model server**, independent of that HTTP admission group. See [server-side generation capacity](#server-side-generation-capacity). This execution bound does not release uncertain SQLite tickets or recover a lost response.

The existing `seulgi-server` CI PMD/CPD analysis is **not migrated or replaced** by this general-purpose bot. Optional A retains its rootless/pinned-image requirements. Company use is deferred to a separate repository after personal development; no PAT support or personal/company authentication-switch framework is added here.

## B intent evaluation (fixed input, never posts)

The offline `intent` command evaluates **text code of any language** through `extract_goals → observe_changes → assess`. It does not read a target checkout, execute target code/builds/tests/hooks, initialize PMD/CPD, require Java or an analysis image, enqueue work, or compose a GitHub publisher. The same core is registered as `intent` in the shared Worker; **B automatic posting remains disabled by default**, including when `publish.mode: comment`.

Prepare a fixed `IntentTaskInput` v1 with `build_intent_task_input(snapshot, base, head, related_paths=())` in `review_bot.application.intent_context`. It contains exactly `schema_version`, the existing service-v2 `snapshot`, full-file `base`/`head` code snapshots, sorted `reviewed_paths`, and `input_hash`. Supply PR/issue original text in `snapshot.evidence`; a text digest alone is not original text. The builder includes changed/rename paths and explicitly related paths, checks file/evidence/inventory hashes and fixed versions, and computes the input hash over the complete record excluding `input_hash`. Serialize it with `dataclasses.asdict` and JSON; do not hand-edit the resulting record or reuse a hash after material changes.

Keep that input in an owned regular **0600/0400** file with no symlink components or hard links. Outputs use owned **0700** directories and **0600** files. Use a fresh output directory for every evaluation: an existing manifest or `B/` namespace is rejected before model setup, not overwritten or automatically repaired.

```bash
rtk proxy uv run --locked review-bot intent --input /path/to/private/fixed-B-input.json \
  --output /path/to/private/evaluation-001
```

Without `--model-profile`, the result is `not_run/model_profile_unset`, with zero review or metering calls. Ambient model opt-in does not enable this command. Explicit profiles are `ollama-local-128k`, `me707-llamacpp` and `macbook-llamacpp`; model preparation is the operator's responsibility, with no model download or provider fallback.

Each valid evaluation stores `B/{input,goals,observations,result,scope,usage,validation}.json`, `B/comment.md` and a mode-specific `manifest.json` with `publication=not_attempted/artifact_only`. Unattempted or invalid stage data is JSON `null`; earlier validated stages and actual call usage survive later failures. Exit `0` means artifacts were saved for a completed or explicitly `not_run` outcome, **not** that a real review completed. Invalid input, unsafe paths, pipeline failure or storage failure exits `1`; no source or raw exception value is printed.

Goals receive PR/issue text only; observations receive full code/test files, change metadata and supplied execution records only, never goals or PR descriptions. Assessment receives the validated two results and original evidence. Duplicate JSON keys, extra fields, invalid types/enums/IDs/quotes, forged SHA/path/line evidence and hypothesis-only conflicts fail closed without another review call. Incomplete prepared scope or input overflow is not replaced by fewer paths, summaries, splitting or truncation. Default B limits are 131,072 input/total context tokens per request and 900 seconds per task, additionally constrained by the existing profile's byte/input/output limits; at most three attempts per stage are permitted. Output entities are bounded to 20 per array, strings to 4,000 characters and evidence references to 128.

Goal/constraint quotes must be literal contiguous spans present in every referenced original text and contain at least **12 non-whitespace Unicode characters**. A shorter quote is accepted only when it equals a complete original `title` or `body` field (after stripping leading/trailing whitespace) in each referenced text record, while still occurring literally in every record. The trusted prompt instructs the model to include surrounding original text in the same contiguous span for brief intent embedded in a longer field, without padding, joining separate spans or rewriting text; short sentences/lines are not additional exceptions. These citation checks do not prove that the statement faithfully represents the quoted meaning.

`usage.calls` counts review-completion attempts. The **Ollama** token counter makes a one-output-token preflight; B includes its separate delivery/usage in total tokens and `model_calls` (normally three review calls plus three generating preflights). The **llama.cpp** native template/tokenizer generates no answer and records zero generation calls/tokens for measurement, so normally only the three review generations count. Metadata/template/tokenizer HTTP requests still share admission. Unknown transport/usage remains `null` with known subtotals, not zero. Supplied `test_run` records are integrity-checked and version/path-bound, **not independently attested**; reading test source never creates a run record. Drafts show scope, unexecuted tests, missing goals/context, and uncertainty, and construct links only from verified evidence.

Synthetic Python/JavaScript/Java fixtures and CLI tests exercise the real B pipeline using mock models/HTTP. They establish integration and validation, not model quality or completion of the live PR #36 evaluation. A v1 records, commands, `A/` artifacts and marker remain unchanged.

### B in the shared Worker (posting opt-in)

In the operator configuration, select `execution.available_modes: [intent]` (or `[architecture, intent]`) and `publish.mode: artifact_only`. Optional `intent.context_paths` is a default-empty list of explicit repository-relative **file** paths for related code/tests; host, traversal, duplicate and trusted-excluded paths are rejected. B reads full regular UTF-8 Git blobs for changed/renamed paths and these related files at fixed comparison-base/head SHAs, not a checkout. Unrequested files are not part of B completeness; absent, excluded or unsupported files remain in the scope, and overflow never reduces it.

When B is available, PR title/body and explicit same-repository references (`#12`, `owner/repo#12`, `https://github.com/owner/repo/issues/12`) are frozen **before selection**. Only the bound repository's issue endpoint is used; issue bodies are not recursively followed. The collector admits at most eight distinct references, 256 KiB per original text, 1 MiB total original text and ten seconds of issue-request time; individual PR/issue responses are capped at 512 KiB. No permissions are widened. Missing references, 403/404, limits and unavailable historical versions are explicit; 401/installation authorization loss aborts the shared run. Source bodies/versions, complete scoped files and missing states affect `context_digest`/`snapshot_id`. Retrieval-time-only changes do not change that material digest; the fixed input still records collection/as-of times and hashes its entire record.

Selected A/B executors run sequentially in the existing SQLite task/lease. A eligibility or empty PMD signals do not exclude B. Existing local/model/Tev selectors accept available subsets independently: Ollama keeps `/v1/systemone`, while the explicit llama.cpp profile uses schema-constrained chat completion for its separate Tev1 model. Mode preparation/review/storage/publication failures preserve the other mode; common collection/authorization failures, PR close, worker stop, deadline or generation/lease loss abort all remaining work. Normal completed/`not_run` outcomes aggregate to `succeeded`; execution/publication failures aggregate to `failed`.

Common `snapshot.json`/`selection.json`/`manifest.json` stay at the run root; A's filenames remain under `A/`, and B stores its stage files under `B/`. Each mode has `receipt.json` (service v2, optional `a_result`/`b_result`, separate usage/delivery/publication); the shared manifest records mode input fingerprints and statuses. A completed core result/usage survives mode-local output failures as well as publication failures. Directories/files remain 0700/0600. SQLite run status is authoritative after external cancellation or lease loss: an interrupted manifest may remain `running`, because the lost owner must not write it.

Publication configuration is independent of mode selection:

| Field | Default / boundary |
| --- | --- |
| `publish.b_marker` | `<!-- review-bot:intent:v1 -->`; must be distinct from the A marker |
| `publish.b_comments_enabled` | `false`; enabling it requires a separate user decision after evaluation |
| `publish.mode` | `artifact_only` always makes no A/B comment writes; service `comment` alone does not enable B |

With B posting disabled, its receipt says `not_attempted/b_comments_disabled` (or `artifact_only`) and private stage files/draft remain available. Even an explicitly enabled B requires a completed validated result and known bot identity; unset profiles, incomplete/oversized inputs and invalid responses are not posted. Each mode creates or updates only its own single bot-owned marker comment. Foreign/other-bot ownership, repeated or ambiguous markers and marker collisions fail closed; no approval/request-changes is submitted. B drafts escape untrusted HTML/markers and generate links only from validated evidence.

Before and after writes, the publisher checks current PR head/target base, open/Draft policy, PR text/context and lease/generation; B also rechecks the used same-repository issues' original contents/versions and missing states. A failed freshness check is not a current successful publication or reusable result. Common authorization loss stops remaining modes while retaining completed results and attempted publication identity. GitHub reads and writes are not atomic; post-write stale/unknown receipts do not imply the comment was never written. Issue-only changes do not enqueue work; sources are recollected at the next PR request.

SQLite adds nullable `publication_receipts.input_fingerprint` non-destructively. Each mode's actual material, prompt/schema, execution/profile configuration and model identity determine its own reuse key; `published_fingerprint` retains its comment-body hash meaning. Only a successful matching individual receipt plus installation/fence and a fresh bot-owned comment/body recheck permits reuse. A whole-run failure or A cache hit cannot hide B's retry/result. Legacy rows remain readable through the legacy A path or safely miss the new cache; they are never assumed to prove B success. No cleanup/retention policy is changed.

### Server-side generation capacity

Keep the existing SQLite review queue and shared HTTP admission. Do not add Redis, a gateway or another scheduler just to enforce this bound. Configure the **existing** llama.cpp launch commands as follows, preserving every other flag:

| Server | Generation flag | Total context flag | Expected `/props` |
| --- | --- | --- | --- |
| Bonsai2 | `--parallel 1` | `--ctx-size 262144` | `total_slots=1`, per-slot `n_ctx=262144` |
| Tev1 | `--parallel 1` | `--ctx-size 131072` | `total_slots=1`, per-slot `n_ctx=131072` |

These are replacement flags, **not complete launch commands or an applied deployment**. Replace conflicting command/environment values rather than appending duplicates. llama.cpp's context flag is the total across slots: changing parallelism without adjusting the former `524288`/`262144` totals would change the per-slot context. Model weights, quantization, KV placement, aliases, ports, private-network binding and authentication stay unchanged.

With this configuration the two server processes can generate at most **one request each, two combined**. Same-model requests serialize; they cannot use the other server's free slot. The server can defer an excess request even while its HTTP connection is open. Client timeout does not prove that the server stopped computing or removed a queued request. This bounds generation in these two processes, not all GPU applications or all metadata HTTP requests.

Apply and verify only when the node is reachable:

1. Identify the actual owner/supervisor for both listening ports and the installed server version. Preserve existing launch settings privately. Historical systemd unit names are not proof of the current manager; do not start a second copy of a server.
2. Pause new generation senders, including evaluation commands and non-bot clients, and confirm active **and deferred** work has drained. A health response or one idle-slot sample alone is insufficient. Do not interrupt someone else's active request to apply the flags.
3. Replace only the parallel/context settings in that existing manager. Restart one idle server at a time through its confirmed supervisor. Do not kill arbitrary processes, recreate services or change network/authentication settings.
4. Check both exact model IDs and `/props` values above. With the two explicit endpoint environment variables set, the existing verification API makes only metadata calls:

   ```bash
   rtk proxy uv run --locked python -c '
   from review_bot.runtime.model_clients import build_review_client, build_selector_client
   for factory in (build_review_client, build_selector_client):
       factory("me707-llamacpp").verify()
   print("model, one-slot, context and template checks passed")
   '
   ```

   These client checks still share HTTP admission and can wait on unresolved tickets. An operator's direct read-only metadata inspection does not release those tickets; do not switch to a fresh admission DB to bypass them.

5. Use short synthetic requests to exercise two requests to one model and one to the other. Observe actual server slots/deferred-work telemetry: no more than one generation per server, the same-model request waits/resumes, and disconnecting a client never raises the bound. Use finite output/deadline limits and drain the test requests before resuming senders. Mock HTTP tests and `/health` alone do not establish this behavior on the installed version.

This does **not** implement automatic uncertain-ticket reconciliation, durable inference results or server-hang recovery. Existing `sent/uncertain` admission records remain intact and may still block new model calls. Neither the one-slot metadata check nor a service restart by itself authorizes clearing them.

## Local Ollama (explicit opt-in)

The local profile `ollama-local-128k` uses two separate models:
- **Review:** `granite4.2:128k` through `/api/chat`, with JSON schema output and `num_ctx=131072`.
- **System 1:** `tev1:0.8b-128k` through `/v1/systemone`. Tev is a decision model, not a chat model; its saved `num_ctx` is verified before use.

With Ollama running and the original models already downloaded, create the 128k tags without overwriting the originals:
```bash
curl --noproxy '*' --fail --silent --show-error http://127.0.0.1:11434/api/create \
  -H 'Content-Type: application/json' \
  -d '{"model":"granite4.2:128k","from":"granite4.2:latest","parameters":{"num_ctx":131072},"stream":false}'
curl --noproxy '*' --fail --silent --show-error http://127.0.0.1:11434/api/create \
  -H 'Content-Type: application/json' \
  -d '{"model":"tev1:0.8b-128k","from":"tev1:0.8b","parameters":{"num_ctx":131072},"stream":false}'
```

Run a local Git/PMD review with Granite (no GitHub publication):
```bash
uv run --locked review-bot review --repo /path/to/java-repo --base main --head HEAD \
  --model-profile ollama-local-128k --format json
```
Without an explicit profile, the existing offline result remains `not_run/model_profile_unset` and makes no model calls. The CLI also accepts `--config` with `model.profile`; the command-line profile takes precedence. Ambient `OLLAMA_HOST` and proxy variables do not redirect model traffic: adapters only accept loopback HTTP origins and reject cloud models.

For the existing `WorkerLoop`, add these fields to a valid operator configuration:
```yaml
model:
  profile: ollama-local-128k
  call_timeout_seconds: 60
  max_attempts: 1
execution:
  selector_uses_model: true
```
The worker composes the two clients separately and preserves explicitly injected clients. `run_once()`/`run_forever()` verify metadata, load Granite **without generating tokens**, then warm Tev before claiming work. This order avoids the observed first-Granite-load eviction of Tev. If claiming manually, call `worker.prepare_models()` **before** claiming a job. Preparation errors leave jobs unclaimed. The `worker` service command supplies the repository, rootless analyzer, job-store and GitHub composition described above; model preparation remains owned by `WorkerLoop`.

Tev routing is on the worker PR-metadata path, not the local Git-review CLI. Definite documentation/assets and known source changes retain their existing local A classification, independently retaining available B; only uncertain paths reach Tev. The 0.75-second selection deadline and conservative available-mode fallback retain A-only behavior. First load, long inputs, inactivity or memory eviction can exceed that deadline; warmup is not a latency guarantee.

### Input and verification boundaries

- Both tags use a 131,072-token context, but this is **not** a full-128k input/quality benchmark.
- Review input is kept intact: the profile has a conservative **90 KiB serialized-input cap** and a 4,096-output-token reserve. Larger inputs return `not_run` without summarization, splitting or truncation. A one-output-token preflight obtains native `prompt_eval_count`; no estimated count is presented as an exact tokenizer result.
- `/v1/systemone` limits the JSON body to **64 KiB** independently of the model context. The existing selector metadata limit still applies; oversized or invalid requests retain architecture review.
- The 128k Granite model used **25.874 GiB** with the original cache settings and **16.064 GiB** with `q8_0` KV cache and Flash Attention. Tev used about **1 GiB**; loading Granite first allowed both 128k models to remain resident on this 32 GiB Mac. Check `ollama ps` and memory pressure before concurrent workloads. A five-minute keep-alive does not prevent eviction.
- Local calls were verified on macOS with Ollama 0.40.1. Ubuntu, full-size inputs, review quality and live GitHub publication require separate validation. Default pytest uses mock HTTP boundaries, not a live Ollama server.

On macOS, these **global, user-approved** cache settings were used for the verification:
```bash
launchctl setenv OLLAMA_KV_CACHE_TYPE q8_0
launchctl setenv OLLAMA_FLASH_ATTENTION 1
```
Quit and reopen the existing Ollama app after setting them. They affect all models and reduce KV-cache precision, not model weights or the configured context. These launch-environment values apply to the current login session; reapply after a new login unless your startup environment supplies them. No automatic startup hook is installed by this project.
